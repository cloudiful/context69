# Query metadata and the composed gate

[简体中文](sqlx-metadata.zh-CN.md)

Context69 compiles its SQL against a committed query cache. `sqlx::query_file*!`
reads a statement from a `.sql` file and matches it against the entries in
`.sqlx`, so a checked statement and the committed cache must stay in step: the
statement's bytes decide the cache entry's identity.

## Ownership

Each crate owns the metadata of its own statements:

- the workspace cache at the repository root (`<workspace root>/.sqlx`) belongs
  to the Context69 crates;
- the pinned `cloudiful-tasks` dependency ships its own `.sqlx` beside its
  manifest and owns the metadata of its own statements. It is resolved from
  `cargo metadata`; the gate below requires the public repository
  `https://github.com/cloudiful/tasks` at
  `rev = 09ca2b383cd489f5a1d8eac697e6f093adbb40b4`, so no cache path or foreign
  crate is allowlisted.

The dependency's metadata is never copied into the workspace cache, and the
workspace cache is never regenerated to silence a native delta. A copied entry is
reported as library metadata absorbed into the application.

## The native check

```sh
DATABASE_URL=postgres://… \
  cargo sqlx --no-dotenv prepare --workspace --check -- \
    --workspace --all-targets --features integration-test-helpers
```

It needs an explicit `DATABASE_URL` in the environment: `.env` loading is
disabled with the CLI's own `--no-dotenv` flag, and the URL is never printed.
The command compiles the workspace with the real database and compares the
freshly described queries with the committed cache.

The two `--workspace` occurrences belong to different commands and both are
required. The first is an option of `cargo sqlx prepare` and keeps one inventory
at the workspace root; the one after `--` is passed to the `cargo check` the CLI
spawns and makes it build every workspace member, including the test targets.
Without the second flag the child checks only the current package, so a member
crate's test-target statements never reach the inventory the check compares —
the same scope the locked offline build below uses.

SQLx 0.9 describes the query macros of an out-of-workspace dependency into that
inventory. When the dependency is compiled in the same run, the inventory
contains its statements as well, and the check fails with

```
error: prepare check failed: .sqlx is missing one or more queries; you should re-run sqlx prepare
```

even though the workspace cache matches the workspace sources. On a warm build
the dependency is not recompiled, the inventory holds only workspace statements,
and the command exits `0`. Both outcomes are normal for this pin; the native exit
code is reported as it is and a red native result is never presented as green.

## The composed gate

```sh
DATABASE_URL=postgres://… python3 scripts/check-sqlx-metadata.py
python3 scripts/check-sqlx-metadata.py --self-test
```

The gate resolves the dependency with `cargo metadata --locked --offline`,
requires the pin above, runs the native command with dotenv disabled, and proves
three conditions:

- **A1** every committed workspace entry was regenerated by the native run and is
  byte-identical to it, with no missing, stale or unused entry, and every entry
  filename is the sha256 of its query bytes;
- **A2** every entry the native run produced beyond the committed cache belongs
  to the pinned library's own `.sqlx` and is byte-identical to it, with no
  metadata missing outside that library and no library entry inside the
  workspace cache;
- **A3** the locked, offline build of the workspace with the helper features
  passes on the two caches as they are.

The comparison always uses the inventory the native run just generated, for both
native outcomes. SQLx exits `0` when the committed cache is a strict superset of
that inventory, so the committed cache is never compared against itself: a
missing or unreadable inventory fails the gate regardless of the native exit
code.

It prints `native_exit`, `native_result`, the consumer and dependency entry
counts, the generated-only and missing counts, the hash mismatches, the offline
build result, the A1/A2 lines and finally `composed_gate=PASS` or
`composed_gate=FAIL`; it exits `0` only when every condition holds. Cargo's own
stderr — a package cache lock wait, for example — is kept as a
`metadata_stderr` diagnostic and never parsed as data: only `cargo metadata`
stdout is read as JSON. A metadata failure or unreadable stdout is reported as a
concise error without a traceback. A native
failure is accepted only as the specific missing-query-set report after a
successful compile; a database, network or compile failure fails the gate. The
gate writes neither cache: the check-mode inventory stays in the build
directory, and credentials and the URL are redacted from everything it prints.

`--self-test` runs the gate's own fixture cases (unknown extra, missing
consumer entry, JSON mismatch, hash mismatch, wrong dependency revision, native
database failure, compile failure, stale check inventory, redaction) with
in-memory data and no cargo or database access.

## Changing the cache

After changing checked SQL, run the DEV prepare command and commit the resulting
entries:

```sh
DATABASE_URL=postgres://… \
  cargo sqlx --no-dotenv prepare --workspace -- \
    --workspace --all-targets --features integration-test-helpers
```

The second `--workspace` is the child `cargo check` argument described above, so
the regenerated inventory covers the same members and test targets the check
compares.

`check-sqlx-metadata.py` is then the proof that the workspace cache, the pinned
library's cache and the offline build agree. The native check alone is not that
proof, because its exit code depends on whether the dependency was recompiled.
