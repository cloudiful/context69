# 向量运行时

Context69 需要向量运行时才能索引和检索库内容：一个生成向量的嵌入提供方，以及一个按实例配置的集合标识与维度存储这些向量的 Qdrant 集合。该运行时是必需的。缺少运行时的实例仍可访问管理界面和 API，但不得声称库处理或检索已就绪。

## 健康检查端点

| 路径 | 回答的问题 | 依赖 |
| --- | --- | --- |
| `/livez` | 进程是否在运行？ | 无。不访问数据库、向量库或模型。 |
| `/readyz` | 本实例当前能否提供核心服务？ | 数据库、当前向量运行时代次、库处理结论。 |
| `/healthz` | 就绪状态。与 `/readyz` 相同的检查。 | 与 `/readyz` 相同。 |

仅当数据库有响应、向量运行时完成一次有界的只读探测、且库处理结论为就绪时，`/readyz` 与 `/healthz` 才返回 `200`。否则返回 `503`，并用字段说明实际失败的部分：

- `status` 在 `200` 时为 `ok`，在 `503` 时为 `degraded`；
- `db_ok` 与 `qdrant_ok` 在 `503` 时分别报告各自结果；
- `library_processing_ready` 报告处理结论，因此即使数据库和 Qdrant 各自正常，`503` 仍然是真实的；
- `indexed_chunks` 仅在 `200` 时出现，因为该值来自成功的探测。

`/healthz` 保持原有响应结构。`/livez` 只报告进程状态：它的 `200` 不代表向量工作可以继续。

探测有界且只读。它在请求开始时读取当时的运行时代次，并在完成时确认代次未变，因此探测期间发生的设置变更或重建会得到 `503`，而不是过期的 `200`。

## 启动与恢复

Qdrant 启动较慢、正在恢复或在启动期间短暂不可达时，无需重启 Context69。启动阶段会在有限预算内重试向量运行时（总计 30 秒，单次最多 5 秒，指数退避）。预算用完时，进程继续提供管理流量，就绪状态保持 `503`。

随后由一个恢复监督器在整个进程生命周期内负责该运行时：

- 尚未发布可用客户端时，按有上限的退避重试；
- 发布客户端后，每 10 秒探测一次，单次上限 5 秒；
- 计划探测失败会将实例标记为未就绪，并保留已发布的客户端供后续探测；探测成功则恢复同一代次；
- 单次请求失败本身不会清除就绪状态；
- 认证、维度、无效配置或已知集合缺失会暂停快速重试，直到配置变更，同时记录经过净化的告警。

对已存在集合的恢复是只读的：检查存在性、标识、维度和计数，绝不创建、删除、重建或重新索引。只有当安装没有任何既有向量状态时才创建集合；并发创建已存在时会重新读取并校验。重建既有集合仍由显式的重建操作及其自身安全门负责。

每个向量使用方都从共享运行时读取一致的嵌入提供方与索引组合，因此恢复后的运行时无需重启即可被库摄取、源同步、翻译、检索、文档存储和重建使用。重建进行期间，写入方与读取方一起停止，直到重建完成；被取代代次的完成不会重新打开就绪状态。

任务引擎还必须在自身的库就绪闩锁通过后才启动：`cloudiful_tasks` schema 存在且归库所有，并且没有存活条目缺少执行分段。闩锁被阻塞时不启动认领调度器、认领维护、Docling 接管或清理，也不启动源清理调度器；HTTP、手动任务 CRUD 和独立服务保持可用；由运维显式处理并重启进程。`docs/operations/task-execution-cutover.zh-CN.md` 是操作手册。

## 嵌入身份变更与重建

嵌入身份由已配置提供方的 base URL、模型和维度组成。API Key 与超时不属于身份：只修改它们会即时生效，且不改动集合。

保存运行时设置时，若在保持维度的前提下修改 base URL 或模型，需要显式确认新网关、别名或模型仍生成相同的向量空间。确认后，本次保存会在与设置相同的事务中确认已持久化的向量身份，并热切换提供方而不重新嵌入任何内容；未确认时会在写入任何密钥或设置之前被拒绝。确认是临时的，只对确认时展示的身份生效，也不代表维度相同就能证明向量等价。

维度变更永远不能通过确认绕过。跨不同维度复用既有向量不在此支持范围内，需要单独的迁移；保存会返回可操作的错误。

启动过程绝不隐式重建或重建集合。当已持久化的身份与配置不一致时，就绪状态保持关闭，运行时通过设置响应报告 `requires_rebuild`；不会发起任何嵌入请求，也不会删除或重建集合。存在数据点但没有已记录身份的集合绝不会被当作空空间接管。真正不存在的集合只会创建一次；已存在且处于配置维度的空集合会被接管并记录为零个分块，因此首次配置仍然可用。

手动重建是唯一会重新嵌入既有数据的路径。它使用当前提供方与集合，在共享重建围栏之后运行，因此重复启动和并发的身份变更都会被拒绝，并且就地替换向量，不删除也不重建集合。成功时记录实际使用的身份并恢复就绪；失败时保持未就绪，绝不报告过期的成功。旧版 `recreate_on_dimension_mismatch` 设置仍为线上协议与配置兼容而接受，但无法授权删除、重建或隐式重建。

## 停止

容器停止时的 `SIGTERM` 与交互停止时的 `SIGINT` 走同一个协调器。观察到首个信号后，进程停止获取新任务，停止调度器、MCP 服务和重排缓存清理，并开始 API 服务的优雅排空。信号被观察时库已发给本副本的认领仍会获得其自有 worker，因此数据库已经接纳的工作不会被静默丢弃。

任务的自然完成与 HTTP 排空共享一个五秒预算，从观察到信号时开始计时。它们不会串行成两个五秒等待，占用的请求也无法延长停止过程。预算耗尽时，进程记录仍有未完成工作后退出。它不会取消正在运行的任务项、写入合成的任务或任务项终态，也不会释放租约：执行租约归条目分段的库所有，域内条目只是镜像它，该租约留给过期处理。进程不会执行自身运行时的异步 drop，因此没有东西代它释放租约；随后由常规过期路径中断库尝试，并把失败投影到条目上。

容器或编排器的停止超时必须大于五秒，以免在该预算完成前杀掉进程。

## 升级恢复

当唯一待执行的迁移是固定版本的内嵌增强残留清理，且该迁移自身的守卫条件仍然匹配已持久化的摄取工作时，启动会进入升级恢复，而不是在 worker 尚未存在时直接失败。进程只在已配置的 API 地址上提供存活与显式未就绪健康检查：`/livez` 返回 `200`，`/readyz` 与 `/healthz` 返回带 `upgrade_pending` 的 `503`。认证、管理、任务、检索、MCP 与调度器路由均不可达。

恢复只启动完成已持久化工作所需的依赖与写入方：任务调度与维护、Docling 远程状态恢复、依赖门、向量监督器以及源清理。常规启动清理、元数据索引 worker、载荷镜像 worker、启动同步和调度器保持关闭。已有的过期库认领按正常租约规则回收：尝试租约过期、尝试被中断，域内条目随之更新；已持久化的 Docling 远程标识会被接管而不是重新提交。远程工作较慢时，进程保持存活但未就绪，并周期性记录守卫计数与已用时间，而不是反复崩溃重启。

守卫条件清除后，先停止任务获取，并等待所有恢复写入方结束，然后由常规 SQLx 迁移器执行未改动的迁移。若出现写入方竞争或与本次迁移无关的错误，进程报告后退出，而不是在未知模式下继续提供服务。迁移完成后，在同一端口重建正常应用，就绪状态重新由数据库、库处理与向量运行时门决定。

该路径依赖本部署已确认的单实例、先停旧再启新的替换方式，不提供多副本写入隔离。未完成的工作仍保留其持久化身份、进度和租约；等待恢复期间沿用停止章节中的五秒预算与部署超时要求。

## 依赖等待

向量运行时无法提供工作时，摄取与源同步按既有依赖协议等待，使用 `qdrant` 依赖键和既有的下次尝试退避。它们不会消耗普通失败次数，也不会改变任务状态或计数。普通的无效输入、模式错误和永久配置错误保持原有失败行为。

## 未配置

没有运行时设置时，API 与管理界面仍可访问，`/livez` 返回 `200`，`/readyz` 与 `/healthz` 返回 `503`。依赖门会报告缺少配置，在运行时配置完成前不会重试模型或网络调用。

## 诊断

恢复日志会标明操作类别、代次和失败类别。日志不包含凭据、端点 URL 中的凭据信息或完整的远端负载。
