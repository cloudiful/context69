# v0.17 Migration — v0.16.0 to v0.17.0

Scope: breaking contract cutover for issue 391. Baseline `v0.16.0`.
Target `v0.17.0`. No production data migration, no business-semantics change
beyond the frozen task-history rules, no v0.16 route deletion except the
retention/purge admin APIs listed below.

Inventory: `docs/contracts/v0.16-inventory.md` (114 operations after issue 391
Task 4: removed `get_task_maintenance`, `update_task_maintenance`,
`purge_tasks`; added user-scoped `clear_task_history`). Canonical kernel:
`crates/context69-contracts` plus domain crates
(`crates/context69-contracts-tasks` for task history shapes).

## 1. No automatic task-history deletion

- The server never auto-deletes any `tasks` row. There is no
  `cleanup_enabled`, no `retention_days`, and no 6-hour task-history cleanup
  loop.
- `completed` (`succeeded`, untrashed) tasks are retained until the user
  explicitly clears them per task or via `POST /v1/tasks/clear`.
- `trash` (trashed terminal) tasks are retained until the user explicitly
  restores them, deletes them per task, or clears the trash view.
- Task deletion never deletes files, PostgreSQL document text, Qdrant
  vectors, or S3 source objects.
- Migration `20260914000000_remove_task_history_retention.sql` drops only the
  unused retention configuration and its scan index:

```sql
DROP INDEX IF EXISTS context69.idx_tasks_terminal_cutoff;
DROP TABLE IF EXISTS context69.task_maintenance_settings;
```

It never deletes `tasks`, `task_items`, `task_attempts`, or
`task_external_jobs` rows. Removed SQL files
(`cleanup_expired.sql`, `purge_terminal.sql`,
`maintenance_settings_get.sql`, `maintenance_settings_update.sql`) have no
runtime callers; removed service methods
(`cleanup_expired_terminal_tasks`, `purge_terminal_tasks`,
`get_task_maintenance_settings`, `update_task_maintenance_settings`) are gone
while dispatcher `maintain_claim_state` and Docling/admin recovery paths stay.

## 2. User clear endpoint (new)

```text
POST /v1/tasks/clear
```

Request (`ClearTaskHistoryRequest`):

```json
{ "view": "completed" }
```

- `view: completed` deletes only the calling user's untrashed `succeeded`
  tasks.
- `view: trash` deletes only the calling user's trashed terminal tasks
  (`succeeded` / `failed` / `cancelled`).
- Active tasks, other users' tasks, and non-matching views delete nothing.
- Only `context69.tasks` rows are deleted (`task_items` / `task_attempts` /
  `task_external_jobs` cascade); library files, documents, vectors, and S3
  objects are untouched.
- Repeated calls are idempotent; the response reports the actual deletion:

```json
{ "deleted_count": 3 }
```

Wire notes:

- Authenticated only (`Bearer`); `400:ApiErrorResponse` on an unknown view.
- Single SQL statement per view (`clear_user_task_history.sql`), strictly
  scoped by `user_id`.
- SDK: raw-only (`client.raw()` operation `clear_task_history` with
  `ClearTaskHistoryRequest` / `ClearTaskHistoryResponse`); no dedicated
  facade method. Per-task `trash_task` / `restore_task` /
  `purge_trashed_task` (`DELETE /v1/tasks/{task_id}`) are unchanged.
- Frontend: the Processing queue exposes `Clear completed` on the Completed
  tab and `Clear trash` on the Trash tab (`clear-completed-button` /
  `clear-trash-button`); the old task-history maintenance panel is gone.

## 3. Removed retention/purge admin APIs

Deleted operations and schemas (server, OpenAPI, SDK raw registry, frontend
types all drop them together):

```text
GET/PUT /v1/admin/tasks/maintenance
POST /v1/admin/tasks/purge
TaskMaintenanceSettings
TaskMaintenanceOverview (retention/purge-only projection)
TaskPurgeMode
PurgeTasksRequest/Response
```

Clients must stop calling these paths. The global `AllTerminal` admin purge
is gone: an admin can no longer bulk-delete completed tasks that have not
entered the trash. Queue UI no longer shows task-history maintenance,
retention windows, `Cleanup expired`, `Purge all terminal`, or
uncertain/isolatable/isolated statistics in the normal queue.

## 4. Retained: lease/source cleanup/Docling recovery

These are execution safety and external-service operations, not task-history
cleanup, and they are unchanged:

```text
POST /v1/admin/tasks/cancel-active
POST /v1/admin/tasks/{task_id}/recover
POST /v1/admin/tasks/{task_id}/recover/queue
POST /v1/admin/tasks/quarantine-submitting
```

Also retained: worker lease recovery and claim maintenance
(`maintain_claim_state`), dispatcher loops, Docling recovery/quarantine
flows, and the source object cleanup dispatcher (release retry/object
cleanup runs on its independent dispatcher with startup drain and 5-minute
fallback poll, decoupled from the deleted task-history loop in issue 389).
`queued/running/waiting/succeeded/failed/cancelled` stay as internal
execution semantics. `TaskListQuery.trashed` and the SDK `delete_task`
deprecated alias keep their v0.16 compatibility boundary; they are not cut
in this release.

## 5. Frontend

- Normal queue shows only `Processing / Completed / Trash`.
- Per-item and bulk user actions stay: retry, trash, restore, permanent
  delete, plus the new clear completed / clear trash.
- Docling recovery/quarantine and cancel-active stay server-side; they are
  not embedded in the normal queue. If an admin ops page is needed later it
  lives outside `ProcessingQueueView`.
- Regenerate after every backend contract change:
  `bun run generate:api:from-backend` (exports
  `frontend/openapi/context69.openapi.json`, then regenerates
  `src/generated/openapi.ts`). Generated files are the contract; never
  hand-edit them.

## 6. SDK (`context69-sdk` 0.17)

- Facade is unchanged except the Task 4 purge-contract removal; canonical
  names from v0.16 stay (`submit_text_batch`, `get_task`, `list_tasks` with
  `TaskListOptions`, `purge_trashed_task` for per-task delete, and the same
  deprecated aliases).
- `clear_task_history` is raw-only; build a `RawRequest` for operation
  `clear_task_history` with a `ClearTaskHistoryRequest` JSON body and decode
  `ClearTaskHistoryResponse`.
- Raw transport covers all 114 operations; retention/purge operations are
  removed and `clear_task_history` is included. `requires_auth=false` stays
  only for `healthz`, `login`, `logout`.

## 7. Deploy together (breaking cutover)

```text
v0.16.0 -> v0.17.0
1. freeze v0.16 clients and keep the v0.16 branch deployable
2. deploy the v0.17 server and the regenerated frontend together
3. publish context69-contracts 0.17 and context69-sdk 0.17 together
4. validate queue tabs (processing/completed/trash), per-task trash/restore/
   permanent delete, and both clear views against production-shaped data
5. retire v0.16 only after the cutover is validated
```

Rules for this release:

- Deploy the v0.17 server and the regenerated frontend together; do not mix
  a v0.16 frontend (maintenance panel, no clear buttons) with a v0.17
  server (no maintenance/purge routes, new clear route).
- Publish the contracts facade and the SDK together; do not mix a v0.16 SDK
  raw registry (purge/retention ops) with a v0.17 server.
- Keep the v0.16 compatibility branch until the deployment switch is done;
  do not migrate or delete task history as part of the deploy.
- No source-data migration in the contract release. No PostgreSQL
  retention, S3 retention, Qdrant indexing, or file/task semantic change
  beyond the frozen history-retention rules.

## 8. Release gate

```bash
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cd frontend && bun run generate:api:from-backend && bun run check && bun run test && bun run build:with-api
git diff --exit-code -- frontend/openapi/context69.openapi.json frontend/src/generated/openapi.ts
```

Plus: workspace, contracts facade, SDK, frontend, and OpenAPI versions are
all `0.17.0` (internal implementation and domain contract subcrates stay at
`0.1.0` / `publish = false`); generated artifacts are clean
(`git diff --exit-code`); production task history has no automatic deletion.

## 9. Rollback

Rollback is a version rollback to v0.16.0 plus the v0.16 frontend/SDK
artifacts. Do not partially roll back only one generated contract layer
(OpenAPI, frontend types, SDK transport move together). Rolling back the
deployment does not restore or delete any task history: this release never
auto-deletes tasks, so there is no data to replay and no history to recover
from the deploy itself.

## 10. Non-goals

- No deletion of `tasks` / `task_items` / `task_attempts` history data.
- No removal of worker lease recovery, Docling recovery/quarantine, or
  source cleanup.
- No change to file, PostgreSQL text, Qdrant, or S3 business semantics.
- No browser verification.
