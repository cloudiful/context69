# v0.18 Migration — v0.17.1 to v0.18.0

Scope: breaking wire cutover for issue 399 (Tasks B0–B3) plus the issue 400
file-state cutover. Baseline `v0.17.1`. Target `v0.18.0`. No v0.17 route
deletion except the flattened upload shapes listed below; the 10
personal-scope `/v1/library/*` routes are deprecated, not deleted.
`migrations/`, legacy migration runtime, and data-compatibility aliases are
retained.

Inventory: 114 OpenAPI operations before and after (no `operationId` added
or removed). Canonical kernel: `crates/context69-contracts` plus domain
crates (`-tasks`, `-library`, `-core`, `-settings`). Wire proof:
`crates/context69-contracts/tests/serde_contracts.rs`
(`b0_*`, `trashed` rejection, B2 canonical-only) plus
`cargo test -p context69 --test contract_surface`.

## 1. File ingest status: only `succeeded` / `failed` (issue 400, breaking)

`LibraryIngestStatus` (`crates/context69-contracts-library/src/library.rs`)
loses `pending`, `running`, and `cancelled`:

```text
before: pending | running | succeeded | failed | cancelled
after:  succeeded | failed
```

- `processing` is no longer a stored file state. It is derived per request
  from active `task_items` (`tree.rs`, `count_processing_by_folder.sql`,
  `list_resources_in_project_folder.sql`). The stored row only ever holds a
  terminal state.
- `cancelled` as a *file* state is gone. Task-level `cancelled`
  (`TaskStatus::Cancelled`, `POST /v1/tasks/{task_id}/cancel`,
  `cancel-active`) is unchanged.
- Writes that produced `pending`/`running` are gone (`set_files_pending`,
  `task_ingest` Running branch, `cancel_file_status` /
  `cancel_active_file_status` SQL, submit-path pending writes). Terminal
  projection (`project_file_status`) and the exhaustion path are the only
  writers.
- One-shot data migration
  `migrations/20260915000000_backfill_stale_file_status_400.sql` reclaims
  rows stuck in `pending` / `running` / `cancelled` with no live
  (`queued`/`running`/`waiting`) `task_items` to `failed` with marker
  `stale pending/running reclaimed by #400`. Rows with live tasks are left
  alone and converge via projection. Rerun is idempotent (matches zero rows
  on repeat).
- OpenAPI `LibraryIngestStatus` is `"succeeded" | "failed"`. Frontend
  `library-status.ts` drops the `running` severity branch; `processing`
  display comes from the derived count, not the stored enum.

Migration:

- Do not send or match on `pending` / `running` / `cancelled` file states.
  Stored `ingest_status` filters take only `succeeded` / `failed`.
- Treat `processing` as a derived UI state (active tasks exist), not a
  persisted value.
- Files reclaimed to `failed` are revived through the normal retry/rerun
  channels; there is no separate restore for the backfill.

## 2. `TaskListQuery.trashed` removed (B1, breaking)

- `TaskListQuery` and `CanonicalTaskListQuery`
  (`crates/context69-contracts-tasks/src/tasks.rs`) drop the `trashed`
  field and gain `#[serde(deny_unknown_fields)]`. Any payload or query
  carrying `trashed` (including old `?trashed=true|false`) fails
  deserialization instead of silently changing meaning.
- The service layer (`services/tasks/mod.rs`) requires `view`
  (`processing` | `completed` | `trash`); a missing `view` is
  `invalid_argument`. The legacy `trashed`/`status`-only fallback and the
  `From` impl's `trashed: None` are gone.
- SQL (`src/sql/db/tasks/list.sql`, `count.sql`) drops the
  `trashed`-boolean branch; only the three `view` predicates remain.
- OpenAPI: `TaskListQuery.trashed` property gone, both query schemas set
  `additionalProperties: false`, `GET /v1/tasks` parameters expose `view`
  and no `trashed`.

Migration:

```text
before: GET /v1/tasks?trashed=true
after:  GET /v1/tasks?view=trash&page=1&page_size=25

before: GET /v1/tasks?trashed=false&status=succeeded
after:  GET /v1/tasks?view=completed&page=1&page_size=25
```

- Always send `view`. `processing` = untrashed non-`succeeded`,
  `completed` = untrashed `succeeded`, `trash` = trashed terminal.
  A user-supplied `status` narrows the view and never widens it.
- SDK `list_tasks` already sends `TaskListOptions.view`; no facade change
  beyond the version bump. Frontend already sends only `view`.

## 3. Upload flattened legacy fields removed (B2, breaking)

Canonical-only wire. Unknown fields (including every legacy key below) are
rejected via `deny_unknown_fields` on the request shapes and on
`IngestOptions` / `CanonicalUploadMetadata`.

Removed types and helpers:

```text
LibraryFileUploadMetadata
LibraryFileIngestOptions (plus ingest_options())
SourcePolicy::from_delete_flag
IngestOptions::from_legacy / legacy_metadata_opt
PrepareLibraryUploadRequest::ingest_options / with_ingest_options
ImportLibraryFileFromUrlRequest::ingest_options / with_ingest_options
FileBatchItem::with_ingest_options (ingest_options() now clones options)
strict_metadata_object compat branch
multipart dual-write and flattened fallback
```

Removed wire fields (all four shapes):

```text
PrepareLibraryUploadRequest: metadata / translation / extraction /
  delete_source_after_processing gone; options: IngestOptions required
ImportLibraryFileFromUrlRequest: same four gone; options required
FileBatchItem: metadata / translation / extraction /
  delete_source_after_processing gone; options: IngestOptions required
UpsertLibraryTextRequest: metadata_json is now MetadataObject
  (explicit object map, was serde_json::Value); non-object rejected;
  deny_unknown_fields
```

Other B2 wire facts:

- Multipart `metadata` parses as `IngestOptions` only. A flattened
  document is `400 invalid metadata JSON`; a non-object
  `metadata.metadata_json` keeps the preserved `422 metadata_json must be
  an object`.
- `CanonicalUploadMetadata` / `IngestOptions` reject unknown keys, so a
  flattened key nested inside `options` also fails.
- Stored worker payload `StoredFileBatchItem`
  (`services/tasks/item_file_processors.rs`) requires `options` and
  rejects flattened keys. `rerun` (`rerun_items.sql`) and the
  unfinished-slot lock (`unfinished_item_file_ids.sql`) copy the stored
  JSON verbatim without deserializing; rejection happens on the next worker
  claim, so in-flight v0.17 rows fail closed instead of silently changing
  ingest semantics.
- Rerun/unfinished audit proved neither path deserializes legacy payloads
  before the worker boundary.

Migration — send only `options`:

```json
{
  "folder_id": null,
  "filename": "a.pdf",
  "media_type": "application/pdf",
  "content_base64": "aGk=",
  "options": {
    "metadata": {
      "external_id": "doc-1",
      "metadata_json": { "agency": "x" }
    },
    "source_policy": "retain"
  }
}
```

- Replace `metadata` / `translation` / `extraction` /
  `delete_source_after_processing` with
  `options: { metadata, translation?, extraction?, source_policy }`.
  `delete_source_after_processing: true` becomes
  `"source_policy": "release_after_processing"`; `false`/absent becomes
  `"retain"`.
- `metadata_json` must be a JSON object (`{}` when empty), never a scalar
  or array.
- SDK: `FileMetadata` (`LibraryFileUploadMetadata`) re-export is gone;
  build `IngestOptions` and set `FileBatchItem.options` /
  `PrepareLibraryUploadRequest.options` directly. Frontend
  `api-group-workspace.ts` already does this.

## 4. Pagination: both shapes kept (B0 audit, not breaking)

`Pagination` vs `OffsetPagination`
(`crates/context69-contracts-core`) are not wire-compatible, so v0.18 keeps
both and documents the boundary instead of migrating:

- Exact totals without window signals serialize identically under both
  shapes (serde snapshot `b0_pagination_audit_*`).
- Only `Pagination` carries `has_more` / `total_is_exact` window signals
  and accepts legacy `page > 10_000`. `OffsetPagination` enforces
  `1 <= page <= 10_000` with exact totals only.
- `TaskPageResponse` stays on `Pagination`; exact-total responses match
  `OffsetPagination` byte-for-byte, windowed or oversized pages require
  `Pagination`. Cursor windows should prefer `CursorPagination`.

Migration: none required. New exact-total code may use either shape for
identical numbers; search windows with cursors use `CursorPagination`.

## 5. B0 canonical rewiring (behavior-preserving)

- Settings service (`services/settings` + `validate` + `mappers` +
  `http_adapters/settings`, `context69-settings-http`) consumes
  `CanonicalUpdateSearchSettingsRequest` (`api_key: SecretPatch`
  `{op: keep|set|clear}`). Legacy
  `UpdateSearchSettingsRequest -> Canonical` conversion is kept only for
  the `keep/set/clear` tri-state proof; the wire is canonical.
- Document queries consume `CanonicalDocumentSort`
  (`field` + `direction: SortDirection`); legacy `order` maps 1:1 and the
  SQL builder binds only validated column names.
- `ApiErrorCode` serialization was proven byte-identical to the legacy
  `code` strings, so handlers now construct the typed
  `CanonicalApiErrorResponse` with zero wire change. Match on `code`, not
  message text.
- Qdrant/embedding substring classifiers (`qdrant_index.rs` timeout and
  idempotent-not-found, `dependency_errors.rs` transient gate) check the
  typed `DomainError` first and fall back to the legacy substrings only
  for transport/server attribution. Downstream `dependency_gate` SQL
  `ILIKE` on persisted strings is untouched.

Migration: none required beyond §4. Keep matching on error `code` strings.

## 6. Personal-scope `/v1/library/*` deprecated (B3, removal in v0.19)

The 10 personal-scope operations are `deprecated: true` in OpenAPI
(`src/api/docs.rs` + handler doc comments) and stay served until v0.19:

| Deprecated (v0.18) | Replacement |
| --- | --- |
| `GET /v1/library/tree` | `GET /v1/groups/by-path/{group_path}/library/tree` |
| `GET /v1/library/resources` | `GET /v1/groups/by-path/{group_path}/library/resources` |
| `POST /v1/library/folders` | `POST /v1/groups/by-path/{group_path}/library/folders` |
| `POST /v1/library/texts` | `POST /v1/groups/by-path/{group_path}/library/texts` |
| `POST /v1/library/folders/{folder_id}/move` | `POST /v1/groups/by-path/{group_path}/library/folders/{folder_id}/move` |
| `DELETE /v1/library/folders/{folder_id}` | `DELETE /v1/groups/by-path/{group_path}/library/folders/{folder_id}` |
| `POST /v1/library/files/upload` | `POST /v1/groups/by-path/{group_path}/library/files/upload` (+ `prepare-upload` for dedup) |
| `GET /v1/library/files/{file_id}` | `GET /v1/groups/by-path/{group_path}/library/files/{file_id}` |
| `POST /v1/library/files/{file_id}/move` | `POST /v1/groups/by-path/{group_path}/library/files/{file_id}/move` |
| `DELETE /v1/library/files/{file_id}` | `DELETE /v1/groups/by-path/{group_path}/library/files/{file_id}` |

Audit: no in-tree typed callers remain (frontend `api-group-workspace.ts`
and SDK facade use only group-scoped routes; MCP tools never touch library
paths). The generic SDK `client.raw()` registry still lists the 10
operations, so pinned external callers could invoke them by
`operation_id` — deletion is deferred to v0.19 instead of happening
silently here.

Migration: move new clients to the group-scoped replacements now; expect
removal in v0.19.

## 7. SDK (`context69-sdk` 0.18) and frontend

- `context69-contracts` 0.18 and `context69-sdk` 0.18 publish together
  (both follow `version.workspace`; internal and domain subcrates stay at
  `0.1.0` / `publish = false`). Raw transport still covers all 114
  operations; flattened upload schemas are gone from the registry.
- Facade: `FileMetadata` alias removed; `FileBatchItem.options`,
  `PrepareLibraryUploadRequest.options`, and
  `ImportLibraryFileFromUrlRequest.options` are required `IngestOptions`.
  `list_tasks` requires `TaskListOptions.view`.
- Frontend: no handwritten wire schemas; group workspace, task queue, and
  settings payloads already send canonical shapes. Regenerate after every
  backend contract change:
  `bun run generate:api:from-backend` (exports
  `frontend/openapi/context69.openapi.json`, then regenerates
  `src/generated/openapi.ts`). Generated files are the contract; never
  hand-edit them.

## 8. Deploy together (breaking cutover)

```text
v0.17.1 -> v0.18.0
1. freeze v0.17.1 clients and keep the v0.17 branch deployable
2. deploy the v0.18 server and the regenerated frontend together
3. publish context69-contracts 0.18 and context69-sdk 0.18 together
4. validate task views (processing/completed/trash), upload/prepare/URL-import
   with options-only payloads, rerun/retry of stored items, derived file
   processing counts, and the deprecated personal-scope routes against
   production-shaped data
5. retire v0.17 only after the cutover is validated
```

Rules for this release:

- Deploy the v0.18 server and the regenerated frontend together; do not mix
  a v0.17 frontend (flattened upload fields, `trashed` query, file
  `pending`/`running` display) with a v0.18 server (options-only,
  `view`-only, terminal file states).
- Publish the contracts facade and the SDK together; do not mix a v0.17 SDK
  (flattened upload fields, `FileMetadata`) with a v0.18 server.
- Run the `20260915000000` backfill once via the SQLx migration runner;
  never modify an applied migration, only add new ones.
- No source-data migration in the contract release beyond the stale-file
  reclaim above. No PostgreSQL retention, S3 retention, Qdrant indexing, or
  task-state-machine change.

Plus: workspace, contracts facade, SDK, frontend, and OpenAPI versions are

(`git diff --exit-code`); stale files show no `pending`/`running` writes.

## 10. Rollback

Rollback is a version rollback to v0.17.1 plus the v0.17 frontend/SDK
artifacts. Do not partially roll back only one generated contract layer
(OpenAPI, frontend types, SDK transport move together). Rolling back the
deployment does not un-reclaim backfilled files: rows the
`20260915000000` migration moved to `failed` stay `failed` and are revived
via retry/rerun after rollback. Per-item code rollback stays single-commit
(B1, B2, 400).

## 11. Non-goals

- No deletion of `migrations/`, legacy migration runtime, or
  data-compatibility aliases.
- No removal of the deprecated personal-scope routes in this release (v0.19).
- No change to the task state machine, file/task deletion semantics, or
  document/Qdrant/S3 business semantics beyond the file-state derivation.
- No browser verification.
