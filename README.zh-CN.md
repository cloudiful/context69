Context69 是一个面向检索的知识库服务，用于导入文档、创建向量索引，并通过 HTTP API 和 MCP 提供搜索能力。

## 功能

- 从 PostgreSQL 数据源导入文本、URL 和文件库文档
- 对文档进行规范化、分块和向量化，并将向量存储到 Qdrant
- 通过 Docling 支持 PDF、DOCX 和 XLSX 转换
- 支持多语言翻译和按语言检索
- 任务历史默认保留，由用户清理（逐条回收站/恢复/彻底删除）；处理队列支持跨页勾选任务并按当前筛选条件捕获整个匹配集合，执行带确认的批量重试/继续/取消/移入回收站，回收站内可批量恢复或彻底删除；管理员取消进行中任务与 Docling 恢复保留在服务端
- 文件库文件、文件夹、数据源和文档采用逻辑删除：搜索墓碑先于任何向量清理提交，因此删除后立即从搜索中消失；清理失败或被中断时会自动重试，不阻塞删除本身。每个墓碑记录其删除提交时所针对的 Qdrant 端点与集合，重试只会从该记录来源移除数据点，因此激活其他集合不会改变清理目标。早于来源记录存在的墓碑不带来源，将保持待清理状态交由人工核实，而不会根据当前设置推测。
- 提供 HTTP API、MCP（HTTP 或 stdio）以及可选的 Web UI

### 运行时切块

切块预算可以按字符或按令牌计量。令牌模式使用明确选择的分词器（`cl100k_base`、
`o200k_base`、固定预设，或已验证的本地 Hugging Face `tokenizer.json` 产物），重叠
部分始终保持在单个切块的预算内。切块区域只有一个分词器控件，用于计量令牌预算，
因此切块预算与令牌计数不会不一致。保存后的
预算立即作用于新建任务，无需重启；已经开始的任务保留其创建时的预算，已存储的文档
不会被自动重新切块。

固定预设是一个固定的上游 `tokenizer.json`：仓库、修订、大小、SHA256 和许可证都是
常量。运行时镜像把 EmbeddingGemma 2 分词器（Apache-2.0）内置在
`<artifact-dir>/<小写sha256>.json`，因此它在启动时即可离线校验并使用，无需准备、
下载或网络访问。归属信息、固定修订和精确哈希列在 `THIRD_PARTY_NOTICES.md` 中，
该文件与 Apache-2.0 许可证文本一同随镜像分发。

没有该内置产物的裸安装仍保留准备流程：准备所选预设只会把该文件下载到可写缓存目录，
在可用之前校验精确大小与哈希，并在运行中的进程内立即生效，无需重启。许可证与来源
链接会在开始准备之前显示。缓存目录为 `./data/tokenizers.cache`，可用
`CONTEXT69_CHUNKING__TOKENIZER_DOWNLOAD_DIR` 覆盖；已准备的预设在重启后会从该
已验证缓存离线加载。就绪状态属于单个进程，因此每个副本都需要内置产物或该已验证
缓存文件才能使用该预设。

挂载产物仍是运维自备文件的高级路径：将标准 `tokenizer.json` 放在
`<artifact-dir>/<小写sha256>.json`，并以只读方式挂载该目录；默认目录为
`./data/tokenizers`，可用 `CONTEXT69_CHUNKING__TOKENIZER_ARTIFACT_DIR` 覆盖。进程在
启动时校验文件名哈希和可读分词器，设置页只提供已验证的产物，并在所选哈希缺失时
失败关闭。新增或移除挂载产物需要重启；已有任务固定过的哈希在其仍可重试期间必须保留。

### Embedding 设置

文档与代码 Embedding 属于各自独立的设置域。文档模型拥有自己的端点、凭据、模型、
可选查询模型、维度和超时。可选的代码 Embedding 区拥有独立的端点、凭据、模型、可选
查询模型、维度和超时，绝不复用文档模型、文档凭据或文档向量。查询模型留空时，分别
沿用对应的文档模型或代码模型。

修改端点、模型或维度即改变该向量空间。现有集合会继续提供服务，直到显式重建并激活
目标集合；在配置身份与活跃身份不一致期间，搜索和入库不可用，操作者仍可取消重建并
保留当前集合。全新安装没有可保留的集合，因此首次索引构建始终是显式操作。经过验证的
激活完成后，被替换的物理集合会在 5 分钟排空宽限期后自动清理。后台维护会在进程重启后
以有上限的退避重试失败的清理，并把集合已不存在视为成功。清理只针对该退役集合记录的
端点执行，且绝不会删除无法证明所属端点的集合，包括没有记录端点或指纹不匹配的旧身份。
早于该行为存在的历史集合不会被回填或扫描清理。

## 部署

### Docker 镜像

发布的镜像位于 GHCR。将 `<tag>` 替换为版本标签，例如 `v0.8.1`。

依赖：

- PostgreSQL：存储应用数据
- Qdrant 和 Embedding 服务：提供搜索和文档导入能力
- Valkey：可选，用于共享会话和调度协调
- Docling：可选，处理 PDF、DOCX 或 XLSX 时需要

```bash
docker volume create context69-library

# 只生成一次主密钥，安全保存，并在所有副本上传递同一个值。
export CONTEXT69_MASTER_SECRET="$(openssl rand -base64 32)"

docker run -d \
  --name context69 \
  --restart unless-stopped \
  -p 80:80 \
  -p 8097:8097 \
  -v context69-library:/app/data/library \
  -e DATABASE_URL='postgres://user:password@db/context69' \
  -e CONTEXT69_APP__MASTER_SECRET="$CONTEXT69_MASTER_SECRET" \
  ghcr.io/cloudiful/context69:<tag>
```

首次启动后访问 `http://localhost`，在设置页面配置 Qdrant、Embedding 服务及其他可选服务，然后重启容器。`80` 端口提供 Web UI 和 HTTP API，`8097` 端口提供 MCP over HTTP。

进行破坏性升级时，请先停止所有运行旧版本的写入进程，再备份 PostgreSQL 与 Qdrant 集合，然后启动新版本。不要让新旧版本的写入进程同时连接同一个数据库，因为新版本写入的数据库结构与向量注册表变更无法由旧代码安全写入。

运行时设置区为未保存的 Qdrant 地址提供测试连接按钮。它使用与索引相同的 gRPC 链路检查可达性（通常是 `6334` 端口，而非 REST `6333` 端口），5 秒超时，只提示成功或脱敏后的失败，不会保存设置、通知观察者，也不要求集合已存在。

Embedding 区将现有模型称为文档模型，并可填写可选的查询模型；留空时查询沿用文档模型。文档与代码 Embedding 使用各自独立的模型和维度。

可选的“代码 Embedding”区为代码块和代码搜索配置独立的 Git 模型。它默认关闭，拥有自己的端点、凭据、模型、可选查询模型和维度，绝不复用文档模型或文档 API Key。关闭时会保留已保存的非密钥字段和代码凭据，除非操作者显式清除该密钥；启用或修改后需要显式重新索引 Git 仓库。

每个 Git 仓库独立选择索引配置（Profile）。`Lexical` 是默认值，只搜索已存储的代码文本。`Hybrid` 和 `FullSemantic` 需要代码模型，并为每个索引代写入独立的代码向量集合：Hybrid 融合词法与向量排名，FullSemantic 按代码向量相似度排名。当代码模型未配置、当前服务代未写入代码向量、记录的代码目标与当前代码身份不一致，或向量运行时不可用时，语义请求会返回词法结果，并通过 `vector_unavailable` 说明原因，而不会冒充语义结果。代码向量使用独立集合，绝不复用文档向量、文档集合或文档凭据。修改代码模型后需要显式重新索引；已有仓库在新配置被修改前保持原配置。注册后仍可编辑跟踪 ref、可选固定提交和索引配置：任一修改都会将已存快照标记为过期，针对旧目标或旧配置启动的索引尝试无法发布。上次索引尝试失败的仓库会返回有界的 `last_error_code` 分类，绝不包含 Provider 消息、响应体或带密钥的细节。

刷新默认手动执行。可选的单仓库间隔独立于文档流水线运行；通过 `/v1/webhooks/{provider}/{external_hook_id}` 接收的已认证 Provider push 也会触发刷新。Webhook 必须使用注册时配置的签名密钥，对原始请求体做 HMAC-SHA256 校验；只有与仓库及跟踪 ref 匹配的 push 事件才会派发工作。若索引已在运行，新请求会留下持久化后续标记而不会丢失，同一仓库也不会同时运行两个索引任务。Webhook 投递按 Provider 投递 ID 幂等；未签名、签名错误、其他仓库或无关 ref 的投递只确认接收，不会触发刷新。

成功索引代按配置的保留总数保留，该总数包含当前活动代：默认值 2 保留活动代加一个历史快照，最小值 1 只保留活动代。更旧、失败和已放弃的索引代会在删除其代码向量后清理。待处理的向量清理会由独立维护任务重试，手动或已停用的源也无需等待下一次索引；索引代会保留待清理记录，避免丢失远端点位的唯一引用。删除仓库会立即停用并阻止新的索引工作；存在活动任务时拒绝删除，待没有写入者后删除向量与元数据，清理无法完成时保留记录并在后续重试。

群组 **Git** 标签页是这条生命周期的用户界面。群组维护者可以注册提供方连接与仓库，并编辑跟踪 ref、固定提交、索引配置、包含/排除规则、间隔、Webhook 开关、保留数量与启用状态。同步会保留同目标空操作，而重建会发送显式强制请求，即使提交与流水线身份未变也会重建当前快照。删除仓库需要确认并会刷新列表。群组查看者可以浏览已索引文件、读取有界的内容窗口，并按代、提交与 ref 溯源执行代码搜索，但不能修改源或连接。

修改 Embedding 模型、网关或维度即改变向量空间。现有集合会继续提供服务，直到显式执行“重建向量索引”并激活目标集合；在配置身份与活跃身份不一致期间，搜索和入库不可用，操作者仍可取消重建并保留当前集合。经过验证的激活完成后，只会把它实际替换的集合安排在 5 分钟排空宽限期后自动删除；清理失败会独立地以有上限的退避重试，绝不会把成功的重建标记为失败。全新安装没有可保留的集合，因此首次索引构建始终是显式操作。重建状态、暂停、继续与取消都是持久化的管理员操作：暂停会让已提交批次先完成再停靠，继续从最后写入的分页之后接着执行，取消则终止本次尝试且不改动现有集合。重建逐文档流式推进：每个文档先切分、暂存，并在有界批次内完成嵌入，然后才推进下一个文档；进度报告已暂存文档数与已嵌入分块数，只有在暂存总数确定后才显示分块总数。暂存向量验证完成后，重建会先执行一次重置，再按有界批次把暂存原始分块安装到实时表，因此激活本身不会执行与发布规模相当的变更。从这次重置直到成功发布清除持久失效标记期间，搜索和入库保持不可用；取消或失败安装会让索引持续失效，直到一次全新的成功重建。完成或取消的暂存数据由现有维护周期按有界批次清理。本版本创建的 token 预算使用 `tokens_v2` 切分路径，旧二进制无法执行：回滚前请完成或取消所有 `tokens_v2` 任务，旧二进制无法继续执行，也不会静默改映射。处理队列可以单独暂停接收新任务；运行中的任务继续执行。

注册表容量统计保留的 point id，而不是向量存储空间。替换只在生产者于删除前记录原始 id、且该条目已属于非活跃集合时释放这些原始 id。没有该来源记录的历史条目仍按全额保留，因此紧张的容量限制可能需要操作者复核或重新重建，而不会进行猜测性折扣。

### 存储的密钥

`CONTEXT69_APP__MASTER_SECRET` 是 Base64 编码的 32 字节密钥，用于加密所有已存储的密钥——Embedding/Search/Docling/翻译服务 API Key、源连接 URL、Git 凭据、Webhook 签名密钥以及浏览器会话签名密钥。只生成一次，请像保管其他凭据一样保管它：没有它，已加密的密钥将无法读取回。轮换它需要执行已配置的密钥轮换流程，而不是重启。

在已有密钥的部署上设置它会转换它找到的内容。启动时，在任何凭据被读取之前，Context69 会使用已配置的密钥分批加密所有仍以旧版明文形式存储的密钥。转换按行、按批次原子进行：如果中途停止，已完成的批次保持加密，下次启动会从剩余部分继续。如果某个已存储的密钥无法加密（例如其密钥名不被当前版本识别），启动会失败，因此部署不会在密钥实际未受保护时却自认为已受保护。未配置主密钥的部署不受影响：其密钥仍可像以前一样以明文读取。

有两点它不会做。这是启动时的转换，不是持续保护，因此**每个会写入密钥的副本都必须配置同一个主密钥**（或者在一个副本转换期间停止其余副本）；没有该密钥运行的实例可能在转换完成后写入新的明文密钥。转换之前的备份仍然包含明文密钥——**context69 不会清理已有备份**，请自行按需处理并按计划淘汰它们。

### 从源码构建

```bash
cargo build --release --bin context69
cd frontend
bun install --no-save
bun run build
cd ..
mkdir -p ci-image-input/frontend-dist
install -Dm755 target/release/context69 ci-image-input/context69
cp -R frontend/dist/. ci-image-input/frontend-dist/
docker build -t context69:latest .
```

运行本地镜像时使用上面的 Docker 命令，并将镜像名替换为 `context69:latest`。

## 测试

后端与前端测试套件只包含快速、隔离的单元测试，无需 PostgreSQL、Qdrant、网络服务、浏览器或外部进程即可运行。

```bash
cargo test --workspace
cd frontend && bun run test
```

前端类型检查与生产构建：

```bash
cd frontend && bun run check
cd frontend && bun run build:with-api
```

端到端行为通过运行中的部署进行人工验收验证，而不是依赖自动化集成、数据库或浏览器测试套件。
