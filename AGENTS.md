# Context69 Notes

- Frontend UI uses Nuxt UI in Vue/Vite mode. Prefer Nuxt UI components, documented props and slots, default interaction behavior, theme tokens, and Lucide Iconify icons before custom controls or style overrides.
- Route-aware navigation UI should follow the named routes in `frontend/src/router/index.ts`; keep breadcrumb and sidebar logic aligned with those route names.
- Frontend API contracts, path parameters, request bodies, and response types must come from `frontend/src/generated/openapi.ts`. Do not use `any`, handwritten schema fallbacks, duplicated request/response interfaces, or manual response annotations to replace generated OpenAPI types.
- When the backend API contract changes, run `cd frontend && bun run generate:api:from-backend`. This exports backend OpenAPI, then regenerates frontend types in order. Include both `frontend/openapi/context69.openapi.json` and `frontend/src/generated/openapi.ts` in the same change.
- After changing frontend code, run `cd frontend && bun run check` before handoff. This checks Vue SFCs and TypeScript without starting the dev server.
- Before handing off frontend/API contract changes, run `cd frontend && bun run build:with-api` plus the affected Vitest files; run the full frontend suite when shared behavior changes. Do not rely on stale or uncommitted generated OpenAPI or component declaration files to satisfy type checking.
- Do not suppress compiler or Clippy diagnostics with `#[allow(...)]`, `#[expect(...)]`, crate-level lint relaxation, or equivalent configuration in production code. Fix the ownership, API shape, data structure, or control flow that causes the diagnostic. A suppression is permitted only for explicitly temporary prototype/demo code, must include a removal rationale, and must not ship as part of a stable feature.
- Release tags are immutable `v<workspace version>` (e.g., `v0.13.2` matches `0.13.2`); never move or force-push an existing tag such as `v0.13.1`. A version bump must synchronously update `Cargo.toml` `[workspace.package] version` (root `context69` follows `version.workspace`) and the `context69-contracts` + `context69-sdk` entries in `[workspace.dependencies]`, `frontend/package.json` `version`, and `frontend/openapi/context69.openapi.json` `info.version` to the same version before creating the new `v<version>` tag. The 10 pinned internal crates stay at `version = "0.1.0"` with `publish = false` and are excluded from release bumps.
- After functional changes have passed their issue-final review and validation, a release-only version synchronization is orchestrator-owned delivery bookkeeping, not a separate implementation phase. Do not launch an executor or repeat the full review/test suite solely for the version bump. Update the required manifests and regenerate OpenAPI/types when needed, then verify matching versions, a clean worktree, an absent immutable tag, and the pushed target commit before tagging. If the release also changes behavior, API schemas, dependencies, or migrations, those changes require the normal implementation and review gates. Higher-priority workflow requirements still apply.
- Local development uses `./scripts/dev.sh full` as the only supported entry point; `./scripts/dev.sh backend` starts only the backend. The full stack serves the frontend on `http://127.0.0.1:5173`, the API on `http://127.0.0.1:8096`, and health checks at `/healthz`.
- A fresh local database creates the development-only bootstrap account `admin` with password `change-me-now`. Existing databases are not reset by bootstrap; if that account already exists, its password may differ. Never use these credentials outside a disposable local environment.
- Use OpenCode browser for exploratory live smoke tests; keep repeatable frontend logic in Vitest and repeatable full-browser flows in the project E2E test suite when one is available.

## Database-backed tests

- Default connection admission is strict. Only in an explicitly operator-confirmed single-user test window without application writers may both preflight and run use `--allow-idle-connections`. It permits only fully visible idle sessions with no transaction; active, transactional, masked/unknown sessions and prepared transactions remain blockers. Idle sessions can become active after observation, so the flag is an operator assertion, not a guarantee. The under-lock recheck uses the same policy. It is invalid with `--list` and never replaces explicit `--authorize-reset` consent. Never terminate sessions or bypass other reset guards to obtain admission.

- Use an explicitly supplied `CONTEXT69_TEST_DATABASE_URL` when available. Otherwise, use the operator-designated `.env` `DATABASE_URL` only as this repository’s test PostgreSQL endpoint; do not inspect `.env` contents or print, log, or persist its URL or credentials. If the endpoint is not securely available or its test designation is unclear, ask the operator.
- For the workspace backend suite, run `./scripts/test-backend.sh --authorize-reset` only after the read-only preflight and explicit reset authorization; never pass a database argument. Before resolving a database target, the runner executes `cargo test --workspace --no-fail-fast --offline` with Cargo's default parallelism, including doctests. During that Cargo stage, database tests and opt-ins remain ignored; the runner selects its ordinary database tests afterward. A pure-suite failure stops before database resolution, preflight, lock, or reset. After that gate, the runner resolves one target from `CONTEXT69_TEST_DATABASE_URL`, or from the operator-designated `.env` `DATABASE_URL` when that variable is unset, and hands it to each database test target through `CONTEXT69_TEST_DATABASE_URL` in the child environment. An ambient `DATABASE_URL` alone never selects a target, and there is no application-config fallback.
- The same PostgreSQL instance and named database are reused across every target: the runner never issues `CREATE DATABASE` or `DROP DATABASE`, never provisions a cluster, container, data directory, or port, and never invents a scratch endpoint. `./scripts/test-backend.sh --preflight` is read-only and reports whether the owned schema may be reset; `./scripts/test-backend.sh --list` needs no database at all.
- Resetting the Context69 schema and its migration ledger inside that designated test database is authorized, and requires the runner's explicit `--authorize-reset` consent. `./scripts/test-backend.sh` forwards your arguments verbatim and never adds that flag for you, so `./scripts/test-backend.sh --authorize-reset` is the supported destructive invocation — run it only after `--preflight` has reported the scope. The reset drops and recreates only the `context69` schema; `public`, installed extensions, and the database itself are preserved, and a reset is refused whenever schema, ledger, or connection ownership is uncertain.
- Do not provision or start a standalone PostgreSQL cluster, container, data directory, or new port for repository tests, and never fall back to an assumed default or production database. Do not reset or drop the shared test instance or its baseline database; clean only the owned `context69` schema or uniquely identified fixture rows.
