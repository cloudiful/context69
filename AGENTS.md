# Context69 Notes

- Frontend UI uses Nuxt UI in Vue/Vite mode. Prefer Nuxt UI components, documented props and slots, default interaction behavior, theme tokens, and Lucide Iconify icons before custom controls or style overrides.
- Route-aware navigation UI should follow the named routes in `frontend/src/router/index.ts`; keep breadcrumb and sidebar logic aligned with those route names.
- Frontend API contracts, path parameters, request bodies, and response types must come from `frontend/src/generated/openapi.ts`. Do not use `any`, handwritten schema fallbacks, duplicated request/response interfaces, or manual response annotations to replace generated OpenAPI types.
- When the backend API contract changes, run `cd frontend && bun run generate:api:from-backend`. This exports backend OpenAPI, then regenerates frontend types in order. Include both `frontend/openapi/context69.openapi.json` and `frontend/src/generated/openapi.ts` in the same change.
- After changing frontend code, run `cd frontend && bun run check` before handoff. This checks Vue SFCs and TypeScript without starting the dev server.
- Before handing off frontend/API contract changes, run `cd frontend && bun run build:with-api` plus the affected Vitest files; run the full frontend suite when shared behavior changes. Do not rely on stale or uncommitted generated OpenAPI or component declaration files to satisfy type checking.
- Do not suppress compiler or Clippy diagnostics with `#[allow(...)]`, `#[expect(...)]`, crate-level lint relaxation, or equivalent configuration in production code. Fix the ownership, API shape, data structure, or control flow that causes the diagnostic. A suppression is permitted only for explicitly temporary prototype/demo code, must include a removal rationale, and must not ship as part of a stable feature.
- Release tags are immutable `v<workspace version>` (e.g., `v0.13.2` matches `0.13.2`); never move or force-push an existing tag such as `v0.13.1`. A version bump must synchronously update `Cargo.toml` `[workspace.package] version` (root `context69` follows `version.workspace`) and the `context69-contracts` + `context69-sdk` entries in `[workspace.dependencies]`, `frontend/package.json` `version`, and `frontend/openapi/context69.openapi.json` `info.version` to the same version before creating the new `v<version>` tag. The 10 pinned internal crates stay at `version = "0.1.0"` with `publish = false` and are excluded from release bumps.
- Local development uses `./scripts/dev.sh full` as the only supported entry point; `./scripts/dev.sh backend` starts only the backend. The full stack serves the frontend on `http://127.0.0.1:5173`, the API on `http://127.0.0.1:8096`, and health checks at `/healthz`.
- A fresh local database creates the development-only bootstrap account `admin` with password `change-me-now`. Existing databases are not reset by bootstrap; if that account already exists, its password may differ. Never use these credentials outside a disposable local environment.
- Use OpenCode browser for exploratory live smoke tests; keep repeatable frontend logic in Vitest and repeatable full-browser flows in the project E2E test suite when one is available.

## Database-backed tests

- Use an explicitly supplied `CONTEXT69_TEST_DATABASE_URL` when available. Otherwise, use the operator-designated `.env` `DATABASE_URL` only as this repository’s test PostgreSQL endpoint; do not inspect `.env` contents or print, log, or persist its URL or credentials. If the endpoint is not securely available or its test designation is unclear, ask the operator.
- For the workspace backend suite, pass the authorized endpoint privately to `./scripts/test-backend.sh --database-url`, preferring `CONTEXT69_TEST_DATABASE_URL` when set and otherwise using the operator-designated `.env` `DATABASE_URL`. The runner creates isolated per-target databases on that same PostgreSQL instance, supplies `CONTEXT69_TEST_DATABASE_URL` to each target, and removes only databases it created. Respect its loopback and non-default-port validation; if the endpoint is rejected or creation is denied, stop and ask the operator.
- Do not provision or start a standalone PostgreSQL cluster, container, data directory, or new port for repository tests, and never fall back to an assumed default or production database. Do not reset or drop the shared test instance or its baseline database; clean only uniquely identified fixture rows or runner-owned temporary databases.
